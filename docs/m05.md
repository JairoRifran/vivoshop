# M05 — Push Notifications Technical Closeout

Hasta hoy, cuando un vendedor salía al aire, el sistema le avisaba a sus
seguidores **escribiendo una línea en el log del servidor**. El producto se
llama compra en vivo y no tenía forma de que nadie se enterara de que empezó un
vivo.

| Marca | Significa |
| --- | --- |
| **AUTOMATED VERIFIED** | Lo prueba la suite, y se comprobó que falla al romperlo. |
| **MANUALLY VERIFIED** | Se ejecutó a mano contra infraestructura real. |
| **NOT VERIFIED** | Escrito, sin evidencia. Dicho así a propósito. |

---

## 1. Domain model

Dos entidades nuevas, y una regla que ya existía y no se cumplía.

`PushSubscription` es un navegador que aceptó recibir avisos. `PushDelivery` es
la constancia de que un aviso ya se decidió para un dispositivo. Y
`Follow.notifyOnLive` —que estaba desde M01— pasó de decorativo a real.

La preferencia vive en el **follow**, no en el dispositivo. Es lo que permite
querer avisos de una tienda y no de otra desde el mismo teléfono, y lo que hace
que apagar una no desconecte el aparato.

```
User
 ├─ PushSubscription  teléfono      ← el dispositivo
 ├─ PushSubscription  notebook
 ├─ Follow Tienda A   notify=true   ← la preferencia
 └─ Follow Tienda B   notify=false
```

---

## 2. PushSubscription

**La identidad es el `endpoint`, y eso decide todo lo demás.**

El navegador entrega una URL a la que el servidor de push del fabricante
reenvía el mensaje. Esa URL **es** la suscripción: el mismo navegador
volviendo a suscribirse obtiene la misma, y si la rota, la vieja deja de
existir. Darle un id propio agregaría una identidad que no manda sobre nada y
abriría la puerta a dos filas para el mismo destino — que en la práctica
significa mandar el aviso dos veces.

Por eso guardar es un **upsert**, no un insert. `createdAt` se conserva: es la
misma suscripción, no una nueva.

`p256dh` y `auth` son las claves con las que ese navegador descifra. No salen en
ningún DTO y no se loguean.

**AUTOMATED VERIFIED** — suscribirse tres veces desde el mismo navegador deja
un solo destino

---

## 3. PushDelivery / idempotency

**Que el endpoint sea único no alcanza, y esa es la corrección más importante
del milestone.**

Una suscripción no duplicada impide mandar dos avisos por tener dos filas. No
impide mandar dos avisos por **intentarlo dos veces**: el proceso muere después
de enviar y antes de anotar, Railway lo reinicia, un barrido reintenta. O dos
réplicas anuncian el mismo vivo a la vez. En los dos casos las suscripciones
están perfectamente deduplicadas y el teléfono suena dos veces igual.

La garantía tiene que vivir donde sobrevive a un reinicio:

```sql
PRIMARY KEY (live_session_id, endpoint, type)
```

Reservar es un `insert … on conflict do nothing … returning`, y devuelve
**solo** los destinos que este proceso reclamó. No hay lectura previa que pueda
quedar vieja entre el `select` y el `insert`: PostgreSQL decide quién gana cada
destino.

**AUTOMATED VERIFIED** — cinco reservas concurrentes reparten cada destino una
sola vez, contra memoria **y** contra PGlite

## 4. notifyOnLive behavior

Dos defectos, encontrados al mirar de cerca.

**Los dos repositorios lo ignoraban.** `listFollowerIds` traía a todos los
seguidores. Mientras nada se enviaba daba igual; con avisos de verdad, no.

**Y no había forma de apagarlo.** `follow` lo guardaba en `true` y nada podía
cambiarlo. Un aviso que no se puede apagar no es una preferencia, es una
imposición — y la única salida que le quedaba a la persona era revocar el
permiso del navegador, que se lleva puestos los avisos de **todas** las demás
tiendas.

```
PUT /stores/:storeId/follow/notifications   { notifyOnLive: boolean }
```

Y se refleja en el detalle de la tienda, para que el interruptor se dibuje en el
estado correcto. Ese último eslabón faltaba y lo encontró una prueba: el
`PUT` funcionaba y la pantalla seguía mostrando encendido lo que ya estaba
apagado.

**AUTOMATED VERIFIED** — apagar, encender de nuevo, y que el detalle lo refleje

## 5. Browser permission UX

**Seguir una tienda y aceptar que te interrumpa son dos decisiones.**

El navegador pregunta **una sola vez**. Gastar esa pregunta en alguien que
apenas tocó "Seguir" —sin saber para qué— es cómo se pierde el permiso para
siempre: quien contesta "no" por reflejo ya no puede arrepentirse desde la
aplicación.

Así que el diálogo es nuestro:

```
✓ Siguiendo

🔔 ¿Querés que te avisemos cuando Jairo Store empiece un vivo?

   [ Sí, avisarme ]   [ Ahora no ]
```

Solo "Sí, avisarme" llama a `Notification.requestPermission()`. "Ahora no" deja
siguiendo la tienda, apaga la preferencia, y **no toca el navegador**.

Los cuatro estados, cada uno con su comportamiento:

| Estado | Qué hace la pantalla |
| --- | --- |
| `unsupported` | Nada que prometa push. Seguir funciona igual. |
| `default` | Ofrece el diálogo propio. |
| `granted` | Registra el dispositivo. |
| `denied` | "🔕 Bloqueadas en este dispositivo". **No vuelve a pedir.** |

La detección comprueba las tres cosas por separado —`serviceWorker`,
`PushManager`, `Notification`— porque fallan por separado.

Y quien dijo "ahora no" no vuelve a ver el diálogo: la respuesta se recuerda en
ese navegador. Insistir en cada visita es cómo un sitio se gana que le bloqueen
los avisos.

**AUTOMATED VERIFIED** — los tres estados, y que no se pida permiso sin que
alguien lo pida primero

## 6. WebPush provider

Detrás del puerto que ya existía, elegido por configuración:

```
NOTIFICATION_PROVIDER=log|webpush     (default: log)
```

Mismo patrón que `mercadopago` junto a `fake`: el default no necesita
credenciales, así que un clon del repositorio sigue arrancando solo.

**El puerto se redefinió como transporte puro.** Antes recibía `userIds` y
resolvía destinos por su cuenta; ahora recibe destinos ya resueltos y ya
reservados, y devuelve qué se entregó y qué está muerto. Decidir a quién
avisarle es una regla del producto y vive en `NotificationService` — la misma
separación que hace que `CommissionPolicy` no viva dentro del adaptador de
Mercado Pago.

Los envíos van en tandas de 50: secuencial, el último llegaría cuando el vivo ya
empezó; todos a la vez, mil envíos abrirían mil conexiones desde el proceso que
está abriendo una transmisión.

## 7. VAPID handling

```
VAPID_PUBLIC_KEY    → puede llegar al navegador (lo necesita para suscribirse)
VAPID_PRIVATE_KEY   → solo el servidor
VAPID_SUBJECT       → mailto: de contacto; los servicios de push lo exigen
```

La pública se sirve desde `GET /notifications/public-key` en vez de incrustarse
en el build: rotarla no exige recompilar y redesplegar la web.

Con `NOTIFICATION_PROVIDER=log` devuelve `null`, y el frontend lo lee como "acá
no hay avisos" y **no le pide permiso a nadie**. Pedir permiso para algo que no
se va a usar es la forma más rápida de perderlo.

Si el proveedor es `webpush` y faltan las claves, el proceso **no arranca**.
`log` sigue funcionando sin ellas.

**AUTOMATED VERIFIED** — clave faltante rechazada al arrancar; `publicKey` null
con `log`

## 8. Service Worker

Los handlers se agregaron **al service worker que ya existía**, no a uno
generado. Las tres reglas de M01 siguen valiendo, y la que más importa es la de
no cachear la API: un archivo generado la perdería sin que nadie lo note hasta
que alguien vea un producto agotado como disponible.

El payload lleva lo mínimo: `type`, `storeId`, `storeName`, `liveSessionId`,
`url`, `title`, `body`. Nada de emails, tokens ni credenciales.

Si el mensaje viene roto se muestra algo genérico en vez de nada: una
notificación silenciosa es peor que una imprecisa, porque el navegador puede
revocarle el permiso a un sitio que recibe mensajes y no notifica.

## 10. Dead subscription cleanup

`404` y `410` son definitivos —el navegador se desinstaló, la persona revocó el
permiso, el endpoint rotó— y la suscripción se borra en el acto. Sin eso la
tabla acumula destinos muertos, cada vivo gasta envíos en gente que ya no está,
y las métricas de entrega mienten hacia arriba.

`429`, `5xx`, timeouts y errores de red **no borran nada**: son el servicio de
push teniendo un mal momento, y desuscribir por eso sería castigar a alguien que
no hizo nada.

**AUTOMATED VERIFIED** — la distinción, en el dominio

## 11. Concurrency guarantees

```
1 vivo  +  1 dispositivo  +  live_started  =  como mucho 1 aviso
```

**La semántica alcanzable, dicha con precisión.** Se reserva **antes** de
enviar, y eso significa *como mucho una vez*: si el proceso muere entre la
reserva y el envío, ese aviso se pierde y nadie lo reintenta.

Es la elección deliberada. Al revés —enviar y después anotar— se conseguiría *al
menos una vez*, con duplicados garantizados ante cualquier reintento. Web Push
no ofrece exactamente-una-vez, así que hay que elegir de qué lado fallar, y el
costo no es simétrico: perder un aviso es una venta que alguien no vio;
repetirlo es alguien que apaga las notificaciones para siempre.

Además, el anuncio se ata al **primer arranque** del vivo. Hoy esa condición no
cambia nada —una reconexión vuelve por `markResumed`, que no anuncia— y se dice
así para no atribuirle un mérito que no tiene. Está porque el costo de
equivocarse es asimétrico.

**AUTOMATED VERIFIED** — anuncios concurrentes, reintentos, y reservas
concurrentes contra los dos drivers

## 12. Multi-device behavior

Una persona tiene tantas suscripciones como navegadores use, y eso es correcto:
quien mira el vivo en el teléfono y compra en la computadora tiene que
enterarse en los dos.

```
3 dispositivos válidos  →  3 avisos
cada dispositivo        →  máximo 1 por vivo
```

Una misma suscripción recibe avisos de todas las tiendas que sigue con el aviso
encendido. No se duplica por tienda.

Esto apareció como un test que fallaba: `expected 4 to be 1`. La aserción
asumía un dispositivo y Ana tenía cuatro. **El código estaba bien y la prueba
estaba mal**, y arreglarla hizo explícito el comportamiento.

**AUTOMATED VERIFIED**

## 13. Security / privacy

Los tres endpoints de escritura exigen sesión, y el `userId` **se deriva del
JWT**, nunca del cuerpo. Se valida que el endpoint sea una URL, que las claves
estén, y que los tamaños sean razonables.

Límites propios, más bajos que el general: 30/min para suscribir y dar de baja,
60/min para la preferencia. Un navegador se suscribe una vez por dispositivo, así
que es holgado para reintentos legítimos y corta a alguien que quisiera llenar
la tabla.

**Dar de baja no exige sesión, y es deliberado.** Quien conoce un endpoint es el
navegador dueño de ese endpoint —no se publica en ningún lado— y lo único que se
puede lograr con él es dejar de recibir avisos. Exigir sesión rompería el caso
que más importa: alguien que revocó el permiso desde el navegador y ya no tiene
con qué pedir la baja.

No se expone quién sigue una tienda, qué endpoints tiene, ni cuántos
dispositivos tiene una persona. **No se agregaron analytics de notificaciones**,
como pedía la especificación.

## 15. E2E

Seis pruebas nuevas, **34 en total**, dos corridas consecutivas desde limpio.

Lo que **no** se prueba: que una notificación aparezca en el centro de
notificaciones del sistema operativo. Playwright no lo puede leer, y una prueba
que dependiera de eso sería frágil sin probar nada nuestro — lo que mostraría es
que Chrome funciona.

Lo que sí: que seguir no pida permiso, que "Ahora no" deje la preferencia
apagada sin tocar el navegador, que el diálogo no vuelva a aparecer, que un
permiso bloqueado no ofrezca nada, y —la condición que cierra el milestone— que
un vivo produzca una sola constancia por dispositivo y uno nuevo vuelva a
producirla.

La frontera del navegador se simula: `Notification.permission` y `pushManager`.
Suscribirse de verdad exige hablar con el servicio de push del fabricante, y eso
no existe en una suite. Todo lo nuestro queda real.

### Lo que las pruebas encontraron

**CORS, y un diseño equivocado detrás.** El navegador mandaba la suscripción
directo a la API con `credentials: 'include'`. Además de chocar con CORS, no
habría llevado la sesión: la cookie vive en el dominio de la web, no en el de la
API. Ahora va por una acción de servidor, como el resto de la aplicación.

**Un interruptor dentro de un encabezado `sticky`.** El click se quedaba
esperando un elemento que flotaba sobre el resto. Se movió al cuerpo, que
además es donde corresponde.

**`notifyOnLive` no llegaba al DTO.** El `PUT` guardaba bien y la pantalla
seguía mostrando encendido lo que ya estaba apagado.

## 17. Real-device verification

**NOT VERIFIED.** Nada de esto se probó todavía en un teléfono.

Lo que hay que hacer, y en este orden:

1. Generar las claves VAPID y cargarlas en Railway junto con
   `NOTIFICATION_PROVIDER=webpush`.
2. **Teléfono comprador:** seguir la tienda → "Sí, avisarme" → aceptar el
   permiso del navegador.
3. **Vendedor:** iniciar un vivo.
4. Comprobar: llega el aviso, dice el nombre correcto de la tienda, y **tocarlo
   abre ese vivo** —no la home—.
5. Esperar, reconectar, interactuar: **no llega un segundo aviso**.
6. Terminar el vivo y empezar otro: **llega un aviso nuevo**.
7. Apagar el aviso de esa tienda y empezar otro vivo: **no llega nada**.

Los pasos 4 y 5 son los únicos que la suite no puede cubrir: el primero depende
del sistema operativo, el segundo del paso del tiempo real.

## 18. Known limitations

1. **Como mucho una vez.** Un aviso puede perderse si el proceso muere entre la
   reserva y el envío. Es la elección deliberada de §11.
2. **El click no está verificado.** El comportamiento de `notificationclick`
   depende del navegador y del sistema operativo.
3. **iOS exige la PWA instalada.** Safari solo entrega push a una aplicación
   agregada a la pantalla de inicio. La detección lo maneja —`unsupported` y no
   se ofrece nada— pero significa que una parte de los compradores no va a ver
   la opción.
4. **Un solo tipo de aviso.** `live_started` y nada más, como pedía la
   especificación.
5. **Sin métricas de entrega.** Se sabe cuántos destinos se reservaron; cuántos
   llegaron de verdad depende de terceros y no se mide.

## 19. Scale boundary

El abanico corre **dentro del proceso que arranca el vivo**, en tandas de 50 y
sin bloquear la transmisión: `announceLiveStarted` no tira nunca, y si el
servicio de push está caído el vivo empieza igual.

Eso alcanza para el orden de magnitud de hoy —decenas o cientos de seguidores—
y el límite está anotado a propósito: **a partir de unos pocos miles de
suscripciones por tienda**, el envío tiene que salir del proceso y pasar a una
cola. La separación ya está hecha —`LiveService` no sabe enviar, y
`NotificationService` es un único punto— así que mover el abanico es cambiar una
implementación, no rediseñar.

La señal para hacerlo: que el arranque de un vivo empiece a tardar de forma
perceptible.

## 20. Remaining debt

1. **La verificación en un teléfono**, §17. Es lo único que falta para poder
   decir que M05 funciona.
2. **`markNotified` se escribe y no se lee.** Guarda cuándo se entregó por
   última vez a cada destino; hoy no lo usa nadie. Sirve para limpiar
   suscripciones dormidas, que todavía no hace falta.
3. **Sin reintento de envíos fallidos transitorios.** Un `503` del servicio de
   push pierde ese aviso; la reserva ya está tomada.
4. **`NotificationChannel` admite `email` y `whatsapp`** y no hay adaptador para
   ninguno. El puerto lo contempla; construirlos es otro milestone.
